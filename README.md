# rendering-patterns

CSR・SSR・SSG などのレンダリング方式を、Next.js 16 で書き分けて比べるサンプルです。
どのページも「時刻を表示するだけ」にそろえて、方式の違いだけが見えるようにしています。

- Next.js 16.4.2（App Router）/ React 19.3
- Cache Components 有効（`create-next-app` の初期設定のまま）

## 動かし方

違いは本番ビルドでしか正しく見えません。`next dev` ではビルド時の事前生成が行われないためです。

```bash
npm install
npm run build   # ルート表の記号で、各ページがどう作られたか分かる
npm start       # http://localhost:3000
```

## 観察のしかた

| 見るもの | 方法 |
|---|---|
| HTML がいつ作られたか | ページをリロードして、表示される時刻が変わるか見る |
| 最初に届く HTML の中身 | `curl -s http://localhost:3000/<path>` で、時刻が HTML に入っているか見る |
| ハイドレーション | `curl` の結果では「未完了」、ブラウザでは「完了」になる。ボタンは完了後にだけ反応する |
| JS がない状態 | DevTools のコマンドメニュー（`Cmd+Shift+P`）で `Disable JavaScript` を選び、リロードする |

ハイドレーションは一瞬で終わるので、普通に開いても切り替わりは目で追えません。
JS を無効にすると、ハイドレーションが起きない状態をそのまま見られます。

- SSR・SSG: 時刻は表示されるが、ハイドレーションは「未完了」のまま。ボタンを押しても反応しない
- CSR: 「読み込み中…」のまま何も表示されない

## CSR（`/csr`）

中身をブラウザで JS が描画します。

- `app/csr/client-clock.tsx` は `"use client"` のコンポーネントで、`useEffect` の中で `/api/now` から時刻を取得します
- `useEffect` はブラウザでしか動かないので、サーバーの HTML には「読み込み中…」しか入りません
- ページの枠（見出しや説明文）はビルド時に事前生成されます。App Router では「ページ全体が空の HTML」にはならず、データの部分だけがブラウザで描画されます

| 観察 | 結果 |
|---|---|
| リロード | 時刻が毎回変わる |
| `curl` | 時刻は入っておらず「読み込み中…」 |

## SSR（`/ssr`）

リクエストのたびにサーバーで HTML を作ります。

- `await connection()` で、ここから先をリクエストが来るまで実行しないよう指定しています
- `export const instant = false` で、ページ全体をリクエスト時まで待たせることを許可しています
  - Cache Components では、ページの一部でも事前生成できるように作るのが基本です。これを外すと、「事前生成できる部分がない」としてビルドが失敗します
  - 本来は、動的な部分を `<Suspense>` で囲んで残りを事前生成するのが推奨です。これは PPR の話なので、別のサンプルで扱います

| 観察 | 結果 |
|---|---|
| リロード | 時刻が毎回変わる |
| `curl` | 時刻が HTML に入っている。ハイドレーションは「未完了」 |

## SSG（`/ssg`）

ビルド時に HTML を作って置いておきます。

- ページの先頭の `"use cache"` で、ページ全体の描画結果をキャッシュします。ビルド時に1回実行され、その結果が配られます
- `export const ensureStatic = "navigation"` で、ページ全体が事前生成されていなければビルドを失敗させます。うっかり動的な処理を足したときの柵です
- `cacheLife("max")` は「30日たったら裏で作り直す」設定です。ビルドのルート表にも `Revalidate 30d` と出ます
  - Cache Components には「二度と作り直さない」設定がないので、厳密にはこれは ISR です。Next.js 16 では SSG と ISR が同じ仕組みで、違いは作り直すまでの期間だけです

| 観察 | 結果 |
|---|---|
| リロード | 時刻はビルドした時刻のまま変わらない |
| `curl` | 時刻が HTML に入っている。ハイドレーションは「未完了」 |

## ISR（`/isr`）

SSG で作った HTML を、期限が過ぎたら裏で作り直します。

- 書き方は SSG と同じ `"use cache"` で、`cacheLife` の期限だけを短くしています（`revalidate: 10`）
- 期限が過ぎた後の最初のアクセスには、古い HTML が返ります。そのアクセスをきっかけに裏で作り直し、次のアクセスから新しい HTML が届きます（stale-while-revalidate）
- `stale` を30秒未満にすると、事前生成の対象から外れて動的な扱いになります。そのため `stale: 30` にしています

本番ビルドで確かめた結果です。

| 経過時間 | リクエスト | 表示される時刻 |
|---|---|---|
| 0秒 | 1回目 | ビルド時の時刻 |
| 12秒 | 期限切れ後の最初 | ビルド時の時刻（古い版） |
| 13秒 | その次 | 12秒時点で作り直した時刻 |

期限を待たずに更新したいときは、`cacheTag` でタグを付けて `updateTag` / `revalidateTag` で消します（`/ppr` の価格で使います）。

## Streaming SSR（`/streaming`）

SSR と同じくリクエストのたびに HTML を作りますが、全部できあがるのを待たずに、できた部分から順に送ります。

- 遅い部分（1秒・3秒かかる部分）を、それぞれ `<Suspense fallback={...}>` で囲んでいます
- Suspense の外側と fallback が最初に送られ、遅い部分はできあがった順に、同じレスポンスの続きとして届きます
- 後から届いた部分は `<div hidden>` に入っていて、一緒に届く小さなインラインスクリプト（`$RC`）が fallback と差し替えます。JS を無効にすると、「読み込み中…」のまま変わりません

本番ビルドで、レスポンスが届くタイミングを計った結果です（`Transfer-Encoding: chunked`）。

| 経過時間 | 届いたもの |
|---|---|
| 0.03秒 | 見出し・最初に送った時刻・2つの「読み込み中…」 |
| 1.02秒 | 1秒かかる部分 |
| 3.02秒 | 3秒かかる部分（ここでレスポンスが終わる） |

`/ssr` と同じ作りで Suspense がなければ、3秒間なにも届かず、3秒後にまとめて届きます。

## PPR（`/ppr`）

1ページの中で、静的な殻はビルド時に事前生成し、動的な穴だけをリクエスト時に流し込みます。
EC サイトの商品ページを例に、4つの部分を置き分けています。

| 部分 | 置き場所 | 理由 | 書き方 |
|---|---|---|---|
| 商品名・説明文 | 殻（SSG） | 全員同じで、ほぼ変わらない | ふつうの JSX |
| 価格 | 殻（ISR ＋ `updateTag`） | 全員同じで、変わる瞬間が分かる | `"use cache"` ＋ `cacheTag("price")` ＋ `cacheLife("hours")` |
| 在庫数 | 穴 | 全員同じだが、常に最新が必要 | `connection()` ＋ `<Suspense>` |
| カートの中身 | 穴 | ユーザーごとに違う | `cookies()` ＋ `<Suspense>` |

- 置き場所は「誰にとっても同じか」と「どれくらいの頻度で変わるか」の2つで決まります
- 特別な設定は要りません。Cache Components では、キャッシュされた部分は自動で殻に入り、`<Suspense>` で囲んだ動的な部分が穴になります
- ビルドのルート表では `◐ (Partial Prerender)` と表示されます
- 価格を変えるボタンは、DB 代わりのファイル（`.data/price.json`）を更新してから `updateTag("price")` を呼びます。期限（1時間）を待たずに、次の表示から新しい価格になります
- 実際の EC では、表示価格がどれだけ新しくても、注文を確定する瞬間にサーバーで DB から価格を取り直す必要があります。このサンプルには決済処理はありません

本番ビルドで確かめた結果です。

| 経過時間 | 届いたもの |
|---|---|
| 0.01秒 | 殻（商品名・説明文・価格）と、2つの「読み込み中…」 |
| 0.04秒 | カートの中身 |
| 1.03秒 | 在庫数（ここでレスポンスが終わる） |

- 価格を変えるボタンを押した直後に、通常のリロードで新しい価格（1,980円 → 2,080円）が表示される
- カートは、Cookie を持つリクエストでは「2点」、持たないリクエストでは「0点」になる。価格は両方で同じ

## RSC（`/rsc/server`・`/rsc/client`）

同じ Markdown を、`marked` というライブラリで HTML に変換して表示します。変換をサーバーの部品でやるか、クライアントの部品（`"use client"`）でやるかだけが違います。

- `/rsc/server`: ページ本体（サーバーの部品）で変換します。`marked` はサーバーでだけ動き、ブラウザには変換後の HTML だけが届きます
- `/rsc/client`: `"use client"` の部品で変換します。ハイドレーションでもう一度変換するので、`marked` の JS もブラウザに送られます

本番ビルドで、各ページが読み込む JS を測った結果です。

| ページ | JS のファイル数 | サイズ（gzip） |
|---|---|---|
| `/`（文章とリンクだけ） | 7 | 173.8KB |
| `/rsc/server` | 7 | 173.8KB |
| `/rsc/client` | 8 | 187.5KB（`marked` を含む1ファイル、13.8KB が増える） |

- サーバーの部品でライブラリを使っても、送られる JS は1バイトも増えません。トップページと同じです
- 逆に、約174KB は React と Next.js の土台で、どのページにも必ず送られます。RSC で減らせるのは、この土台の上に乗る部品の分だけです
- これまでのページもすべて RSC です。ハイドレーションされているのは、`"use client"` を付けた `HydrationCheck` と `ClientClock` だけです

## Islands Architecture（`frameworks/astro-islands`）

Astro 7.4 と Vue 3 で作った、別のプロジェクトです。動かし方と詳細は [frameworks/astro-islands/README.md](frameworks/astro-islands/README.md) にあります。

- ページは静的な HTML のままにして、`client:load` や `client:visible` を付けた部品（島）だけをハイドレーションします
- 島のないページの JS は 0 です。島のあるページでも、Vue の本体を含めて gzip 約31KB です
- Next.js は、文章だけのページでも土台の JS（gzip 約174KB）を送ります。動く部品がほとんどないサイトなら、Islands の方が送る JS をずっと減らせます

## Resumability（`frameworks/qwik-resumability`）

Qwik 1.20 で作った、別のプロジェクトです。動かし方と詳細は [frameworks/qwik-resumability/README.md](frameworks/qwik-resumability/README.md) にあります。

- ハイドレーションをしません。ボタンの HTML には `on:click="q-xxx.js#s_xxx"` という「押されたら読み込む処理の住所」だけが入り、状態は `<script type="qwik/json">` に埋め込まれます
- 読み込み時に実行される JS は約4KB（gzip）で、部品のコードは押されるまで実行されません
- ただし、押したときに待たせないよう、Qwik の本体（gzip 19.7KB）などは先読みでダウンロードしています。減るのはダウンロードではなく、読み込み時の実行です

## ステップ3のまとめ（読み込み時にブラウザで実行される JS）

| 方式 | ページ | 実行される JS（gzip） |
|---|---|---|
| 全体のハイドレーション＋RSC（Next.js） | 文章とリンクだけのページ | 約174KB |
| Islands（Astro） | 島のないページ | 0 |
| Islands（Astro） | Vue の島があるページ | 約31KB |
| Resumability（Qwik） | ボタンが1つのページ | 約4KB（ほかに約21KB を先読みで取得） |
